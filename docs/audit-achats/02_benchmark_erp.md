# 02 — Matrice canonique de capacités du module Achats (procure-to-pay)

Date : 2026-10-11. Synthèse des six référentiels du dossier `reference/` : SAP S/4HANA MM + Ariba (**SAP**), Oracle Fusion Procurement + EBS (**ORA**), Dynamics 365 SCM/Finance (**D365**), Odoo 17/18 (**ODOO**), NetSuite (**NS**), verticaux agro + réglementaire marocain (**VERT**). Cible : ERP interne boulangerie-pâtisserie, Maroc, ~40 fournisseurs, ~300 BC/an, 2-3 personnes achats/compta, 1 magasinier. Lecteur : ancien développeur Oracle Forms / PL*SQL.

## 0. Méthode et conventions

- **Fusion** : une capacité canonique = un identifiant stable `C-Dx-nn`. La colonne « ERP » donne, pour chaque référentiel qui l'offre nativement, le nom ou l'identifiant utilisé dans le document source (ex. `SAP C03`, `ORA D1.6`, `D365 D1.8`, `ODOO D1.2`, `NS D1.5`, `VERT A.1`). Un référentiel qui ne l'offre que par add-on/SuiteApp ou en édition Enterprise est noté `(EE)` ou `(add-on)` et n'est pas compté comme natif.
- **Niveau** (règle de la mission) : **socle** si ≥ 4 référentiels l'offrent nativement ; **standard** si 2-3 ; **avancé** sinon (1 seul, ou spécifique Maroc/agro). Le référentiel VERT compte comme un référentiel.
- **Pertinence cible** : **essentiel** (sans elle le module n'est pas crédible pour cette boulangerie ou la loi marocaine l'exige), **utile** (valeur claire à 300 BC/an, à planifier), **optionnel** (valeur faible à cette échelle, prévoir le schéma au plus), **hors-sujet** (grands comptes / autre contexte ; conservé pour mémoire).
- **Indice de modélisation** : fourni pour essentiel et utile ; il retient le meilleur pattern parmi les ERP et le rattache aux tables existantes du dépôt (`suppliers`, `purchase_orders`, `purchase_order_items`, `reception_vouchers`, `reception_voucher_items`, `ingredient_lots`, `invoices`, `invoice_items`, `invoice_purchase_orders`, `payments`, `scheduled_payments`, `purchase_requests`, `inventory_transactions`, `packaging_items`, `expense_categories`, `account_auxiliaries`, `reception_quality_checks`). Les noms proposés sont indicatifs.
- **Contraintes projet respectées partout** : unités affichées = unités saisies (conversion interne seulement) ; catégories unifiées `expense_categories` ; routage consommable/ingrédient par catégorie (`fn_purchasable_kind`, mig 207) → on garde `(purchasable_kind, purchasable_id)` plutôt que deux jeux de colonnes ; contenants portés par l'ingrédient (mig 225/226) mais **figés sur la ligne** à la commande ; TVA par ligne (mig 189) ; ledger existant avec auxiliaires 4411 (`account_auxiliaries`).
- Analogie Oracle permanente : document = bloc maître/détail Forms ; compteur dénormalisé = colonne entretenue par trigger `AFTER` ; statut dérivé = vue ou fonction ; pièce comptabilisée = jamais d'`UPDATE`, contre-écriture.

## 1. Processus canonique cible (document flow)

Les six référentiels convergent sur la même chaîne ; le dessin ci-dessous est la cible, avec les tables du dépôt entre crochets.

```
BESOIN                                   D2
 ├─ point de commande / min-max (stock + en commande − besoins plans)     [reorder_rules]
 ├─ plan de production confirmé → besoins nets en unité de base (BSI)      [production_* → purchase_requests]
 ├─ demande manuelle (atelier, boutique) / liste du jour                   [purchase_requests + lignes]
 └─ rupture / transfert interne (sans fournisseur)                          [transfer/rupture requests → même modèle]
        │  statut de couverture PAR LIGNE : pending → partially_ordered → ordered → received → closed
        ▼
SOURCING & APPROBATION                   D3
 ├─ (optionnel) demande de prix à N fournisseurs → comparatif en MAD/kg → attribution → fiche article×fournisseur
 ├─ détermination de la source : préféré / autorisé / bloqué, tarif daté ou contrat cadre
 └─ règles d'approbation (montant, catégorie, hors-tarif, espèces) → tâches → historique append-only
        ▼
BON DE COMMANDE                          D4        [purchase_orders / purchase_order_items / (po_schedules)]
   type : stock | charge | cadre | retour | bon d'achat interne (marché)
   ligne : (kind,id) + contenant figé + qty_contenant + qty_base + prix/contenant + remise + TVA + catégorie
   draft → submitted → approved → sent (version 0, PDF horodaté) → [acknowledged] → clôturé / annulé
   toute modification après envoi = version n+1 + motif + re-approbation si champ contrôlé
   compteurs par ligne : commandé / reçu / accepté / facturé / annulé  ← DÉRIVÉS des événements
        ▼
RÉCEPTION & QUALITÉ                      D5        [reception_vouchers / reception_voucher_items → rcv_events]
   liste des attendus du jour → saisie en contenants (+ poids réel pesé) → lot fournisseur + DLC obligatoires (périssables)
   → lot interne [ingredient_lots] → statut quarantaine/disponible → contrôle (checklist, photo, motif)
   → mouvement de stock valorisé au prix BC [inventory_transactions] → écriture Dt stock/charge  Ct GR/IR (4081)
   partielle (reliquat ouvert ou annulé explicitement) · correction (contre-événement) · retour (motif → avoir attendu)
        ▼
FACTURE FOURNISSEUR & RAPPROCHEMENT      D6        [invoices / invoice_items / invoice_purchase_orders]
   saisie référencée (réceptions non facturées du fournisseur) ou sans BC (charges) · pièce jointe
   contrôle mentions légales (ICE/IF/TP…) · anti-doublon (fournisseur, n°) · TVA par ligne vs taux daté attendu
   match PAR LIGNE : qté facturée ≤ reçue non facturée ; prix vs BC ; tolérances → holds par ligne → blocage paiement
   validation_status ⊥ approval_status ⊥ payment_status · avoir rapproché / débit-crédit ultérieur
   écriture : Dt GR/IR (prix BC) + Dt écart prix (ou stock) + Dt TVA  Ct 4411 auxiliaire
        ▼
PAIEMENT & TRÉSORERIE                    D7        [scheduled_payments / payments / (payment_applications)]
   échéancier par facture (conditions) → proposition de la semaine (hors holds) → paiement N:N (lettrage)
   mode typé (espèces plafonnées 5 000 MAD/j/fournisseur, chèque barré, virement, LCN) · acomptes · void
   TVA récupérable à la date de paiement · balance âgée · rapprochement bancaire
        ▼
COMPTABILITÉ & PILOTAGE                  D8 / D9   [ledger existant]
   une pièce = une écriture équilibrée (source_type, source_id) · GR/IR lettré par ligne de BC · PMP / coût lot
   reçu non facturé, écarts prix, dépenses, prix au kg dans le temps, OTIF fournisseur, états TVA/journal des achats
```

Trois invariants à ne jamais casser (communs aux six sources) : (1) les quantités vivent au niveau le plus fin (ligne, voire échéance) et l'en-tête n'a qu'un statut dérivé ; (2) aucune pièce ayant eu un effet stock ou compta n'est modifiée ni supprimée : correction = nouvelle pièce liée ; (3) tout ce qui est copié d'un référentiel dans une ligne (prix, facteur de conversion, tolérance, délai) est un **snapshot** figé.
