Analogie Oracle utilisée tout au long : le BC est un bloc maître/détail Forms ; un « compteur dérivé » est une colonne entretenue par un trigger `AFTER INSERT` sur une table d'événements (jamais un `UPDATE` applicatif) ; un « statut dérivé » est une vue ou une fonction PL/pgSQL ; un trigger `BEFORE UPDATE` qui refuse une modification joue le rôle d'un `WHEN-VALIDATE-RECORD` infranchissable par l'API.

### G-D4-03 — Ligne de BC sans double unité, sans facteur figé, sans TVA/remise/catégorie — **P0**

- **Capacités** : C-D4-03 (essentiel) ; aussi C-D1-06, C-D5-01, C-D6-04, C-D9-05 (pattern P3). **Faiblesses** : W-35, W-44, W-01 (partie BC), W-16 (partie BC).
- **Preuves** :
  - Schéma `purchase_order_items` (`schema_d.txt`) : `id, purchase_order_id, ingredient_id, packaging_id, quantity_ordered, quantity_delivered, unit_price, created_at` — aucune unité, aucun contenant, aucune TVA, aucune remise, aucune catégorie.
  - Unité et contenant lus à la volée : `po-repo:80-95` (`COALESCE(ing.unit, pkg.unit) as ingredient_unit`, `ing.container_size`, `ctc.label`), idem `po-ctrl:305-315` pour le PDF.
  - Règle contenant appliquée à la création (`po-repo:152-154`, `container-rule.ts`) mais le résultat n'est stocké qu'en unité de base : le nombre de contenants commandé est perdu.
  - SQL : `SELECT COUNT(*) FILTER (WHERE ing.container_size IS NOT NULL), COUNT(*) FROM purchase_order_items poi JOIN ingredients ing ON ing.id=poi.ingredient_id` → **49 / 658** lignes dont l'ingrédient a un contenant sur la fiche, sans snapshot sur la ligne.
  - SQL : unités des lignes ingrédient : kg 386, unit 205, l 41, g 26 — l'unité `g`/`unit` sur 231 lignes rend le « prix unitaire » ambigu (prix de la pièce ? du gramme ? du carton ?).
  - TVA : mig 189 n'a ajouté `tva_rate` que sur `invoice_items` ; `createInvoiceFromPo` insère `tax_amount = 0` (`rv-repo:168-176`) faute d'information sur le BC ; SQL : 263/294 factures auto à TVA 0.
  - Volatilité symptomatique (rapport BC §2.8, SQL re-exécutée) : Eau de fleur d'oranger 4 → 235 DH, Kiwi 0,04 → 53 : changements d'unité de saisie non détectables.
- **Manque vs standard** : SAP (triplet d'unités + snapshot), Oracle (`conversion_to_stock` figé), D365 (`PurchQty`/`QtyOrdered`), Odoo (`product_qty`/`product_uom_qty`) stockent tous la quantité saisie **et** la quantité de base avec un facteur figé sur la ligne, un prix exprimé dans l'unité d'achat, une remise et une taxe par ligne.
- **Impact métier** : le prix saisi alimente `ingredients.unit_cost` → coût de toutes les recettes (`v_recipe_direct_cost`) et valorisation ; une saisie « 180 DH le sac » enregistrée comme « 180 DH/kg » multiplie le coût matière par 25 sans alerte ; la contrainte projet « 420 g reste 420 g » n'est pas tenue sur le BC ; TVA récupérable perdue en amont.
