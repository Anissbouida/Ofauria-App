## (b) Fiches d'écart

### G-D6-01 — La facture n'est pas la pièce du fournisseur : pas de type, de n° fournisseur obligatoire, de dates distinctes ni de montants déclarés

- **Capacités / faiblesses** : C-D6-01 ; W-17, W-67, W-71.
- **Preuve** :
  - `\d invoices` (schema_d.txt:114-140) : `invoice_number varchar(50) NOT NULL` **sans index unique** ; pas de `kind`, `received_on`, `accounting_date`, `declared_ht/vat/ttc`, `source`, `updated_at`.
  - `createInvoiceFromPo` (`server/src/repositories/reception-voucher.repository.ts:138-149`) : n° = dernier `reception_vouchers.supplier_invoice_number` du BC, sinon `generateInvoiceNumber('received')` → `FR-YYYY-NNNN` ; date = `COALESCE(supplier_invoice_date, CURRENT_DATE)` (`:168-171`).
  - SQL Q10 : 250/317 factures reçues portent un numéro interne `^(FR|FA|INV)-`. Q17 : 3 BR portent un n° fournisseur différent de celui de leur facture (numéro perdu). Q25 : 14 factures datées avant la réception ; 21 saisies > 7 j après la date facture ; 13 paiements antérieurs à la date facture.
  - `invoices.reception_date` écrit par le formulaire libre mais jamais lu par une requête métier (`grep -rn reception_date server/src/repositories` → uniquement les INSERT/UPDATE).
- **Manque vs standard** : SAP RBKP, Oracle AP_INVOICES, Odoo `account.move` portent tous : numéro du fournisseur (clé de doublon), date de la pièce ≠ date de réception du papier ≠ date comptable, type de pièce (facture, avoir, débit/crédit ultérieur, acompte, bon interne), montants **déclarés** par le fournisseur comparés à la somme des lignes (hold `DIST_VARIANCE`), source de création.
- **Impact métier** : 80 % des factures sont inutilisables comme pièce fiscale (CGI art. 146) ; impossible de rapprocher un relevé fournisseur (Ecomab : 11 factures ouvertes, 35,6 k DH) ; la date facture = jour de frappe fausse la période de TVA et l'ancienneté des dettes.
- **Priorité** : **P0** (traçabilité réglementaire).
- **Conception cible** :
  ```sql
  -- mig 304_invoices_structure.sql
  ALTER TABLE invoices
    ADD COLUMN kind text NOT NULL DEFAULT 'invoice'
      CHECK (kind IN ('invoice','credit_note','subsequent_debit','subsequent_credit','prepayment','internal_voucher')),
    ADD COLUMN supplier_invoice_number text,          -- vérité fournisseur ; invoice_number reste la clé interne
    ADD COLUMN received_on date,                      -- réception du papier
    ADD COLUMN accounting_date date,                  -- date d'écriture (période ouverte)
    ADD COLUMN declared_ht numeric(12,2), ADD COLUMN declared_vat numeric(12,2), ADD COLUMN declared_ttc numeric(12,2),
    ADD COLUMN source text NOT NULL DEFAULT 'manual' CHECK (source IN ('manual','from_receipt','import','voucher','recurring','legacy_auto')),
    ADD COLUMN settles_invoice_id uuid REFERENCES invoices(id),   -- avoir → facture d'origine
    ADD COLUMN payment_mode_declared text,            -- mention « mode de paiement » (R1)
    ADD COLUMN updated_at timestamptz, ADD COLUMN updated_by uuid REFERENCES users(id);
  CREATE UNIQUE INDEX ux_invoices_supplier_number
    ON invoices (supplier_id, lower(regexp_replace(supplier_invoice_number,'\s','','g')))
    WHERE invoice_type='received' AND kind IN ('invoice','credit_note') AND validation_status <> 'cancelled';
  ```
  `invoice_number` interne devient un numéro sans trou pris à la **validation** (P13, `document_sequences(doc_type='FR', year, last_no)` + `fn_next_doc_no`), brouillons sans numéro.
  - Règle : `supplier_invoice_number NOT NULL` exigé au passage `draft → validated` pour `kind IN ('invoice','credit_note')` ; `kind='internal_voucher'` en est dispensé (G-D6-18).
  - Endpoints : `POST /invoices` (brouillon, zod `createInvoiceSchema` : `kind`, `supplierId`, `supplierInvoiceNumber`, `invoiceDate`, `receivedOn`, `declared{Ht,Vat,Ttc}`, `lines[]`) ; `PATCH /invoices/:id` limité à `draft` ; `POST /invoices/:id/validate` (G-D6-08).
  - Écran : `features/purchasing/invoices/InvoicePage.tsx` = en-tête (fournisseur, n° fournisseur, 3 dates, déclaré HT/TVA/TTC) + `odoo-table` des lignes + bandeau `StatusBanner` « Σ lignes 1 234,00 ≠ déclaré 1 240,00 (écart 6,00) ». `ui-timeline` : brouillon → validée → approuvée → comptabilisée → payée.
- **Reprise** : `UPDATE invoices SET supplier_invoice_number = invoice_number WHERE invoice_number !~ '^(FR|FA|INV)-'` (67 factures) ; les 250 `FR-` restent `supplier_invoice_number NULL`, `source='legacy_auto'`, à compléter via un écran « factures à régulariser » (liste filtrée `supplier_invoice_number IS NULL AND kind='invoice'`) ; `received_on := created_at::date`, `accounting_date := invoice_date`.
- **Effort** : M. **Dépendances** : G-D6-08 (statuts), G-D6-11 (index unique). **Risques** : l'index unique partiel doit exclure les `FR-` historiques (sinon les 23 factures d'import sans n° fournisseur bloquent) → filtre `supplier_invoice_number IS NOT NULL` implicite par l'expression.

### G-D6-02 — Pas de facture « depuis les réceptions non facturées » : une seule facture par BC, uniquement en livraison complète

- **Capacités / faiblesses** : C-D6-02, C-D6-03 ; W-49, W-12 (partie facture).
- **Preuve** :
  - `createInvoiceFromPo` : `SELECT id FROM invoices WHERE purchase_order_id = $1 AND status != 'cancelled' LIMIT 1` → `return null` (`reception-voucher.repository.ts:85-89`) ; déclenchée seulement `if (newStatus === 'livre_complet')` (`:536-545`).
  - `generateInvoice` (`purchase-order.repository.ts:564-605`) exige `livre_complet` et 0 ligne sans prix ; un BC `en_attente_facturation` qui passe `livre_complet` par édition ne génère rien : SQL « BC livrés sans facture » = 4 `livre_complet` (4 346,20 DH) + 1 `en_attente_facturation` (BC-2026-0230).
  - Q18 : 2 BC ont ≥ 2 BR avec des n° de facture fournisseur **distincts** ; le `ORDER BY created_at DESC LIMIT 1` (`:138-144`) ne garde que le dernier.
  - Aucune vue « reçu non facturé » : `grep -rn "non factur\|invoiceable\|uninvoiced" server/src` → uniquement le widget BC `has_invoice`.
- **Manque vs standard** : SAP MIRO propose les postes de réception non facturés ; Odoo `qty_to_invoice = qty_received − qty_invoiced` par ligne ; NetSuite « Bill Purchase Orders » en lot. La facture se **choisit** parmi les réceptions ouvertes du fournisseur (multi-BC, multi-BR, partielle), elle n'est pas un sous-produit du dernier BR.
- **Impact métier** : les fournisseurs à délai (Ecomab 27 factures, OVOTEC 15) livrent plusieurs fois par mois et facturent par livraison ou par quinzaine ; aujourd'hui soit on force un BC par livraison, soit la facture est fausse. Les 8 BC multi-BR sont illisibles.
- **Priorité** : **P1** (le workflow quotidien de l'acheteur en dépend ; P0 pour la cohérence si G-D6-03 n'est pas fait).
- **Conception cible** :
  ```sql
  ALTER TABLE invoice_items
    ADD COLUMN purchase_order_item_id uuid REFERENCES purchase_order_items(id),
    ADD COLUMN receipt_item_id uuid REFERENCES reception_voucher_items(id),
    ADD COLUMN line_kind text NOT NULL DEFAULT 'item' CHECK (line_kind IN ('item','expense','freight','misc')),
    ADD COLUMN qty_container numeric(12,3), ADD COLUMN qty_per_container numeric(12,4),  -- snapshot P3
    ADD COLUMN corrected_item_id uuid REFERENCES invoice_items(id);
  CREATE INDEX ix_ii_receipt_item ON invoice_items(receipt_item_id) WHERE receipt_item_id IS NOT NULL;
  -- reçu − facturé par ligne de réception (quantités signées : avoirs négatifs)
  CREATE VIEW v_receipt_items_invoiceable AS
  SELECT rvi.id AS receipt_item_id, rv.purchase_order_id, po.supplier_id, rvi.ingredient_id, rvi.packaging_id,
         rvi.quantity_received,
         rvi.quantity_received - COALESCE((SELECT SUM(ii.quantity) FROM invoice_items ii JOIN invoices i ON i.id=ii.invoice_id
             WHERE ii.receipt_item_id = rvi.id AND i.validation_status <> 'cancelled'),0) AS qty_to_invoice,
         COALESCE(rvi.unit_price, poi.unit_price) AS expected_unit_price
  FROM reception_voucher_items rvi JOIN reception_vouchers rv ON rv.id=rvi.reception_voucher_id
  JOIN purchase_orders po ON po.id=rv.purchase_order_id JOIN purchase_order_items poi ON poi.id=rvi.purchase_order_item_id;
  ```
  - Endpoints : `GET /suppliers/:id/invoiceable` (lignes de `v_receipt_items_invoiceable` à `qty_to_invoice > 0`, groupées par BR) ; `POST /invoices/from-receipts {supplierId, supplierInvoiceNumber, invoiceDate, items:[{receiptItemId, qty, unitPrice, tvaRate}]}` → facture `draft` avec `source='from_receipt'`, refus si `qty > qty_to_invoice` (sauf tolérance G-D6-06).
  - `invoice_purchase_orders` devient une **vue** dérivée des lignes (`SELECT DISTINCT invoice_id, purchase_order_id FROM invoice_items JOIN reception_voucher_items ...`) ; `invoices.purchase_order_id`/`reception_voucher_id` conservés en lecture seule pour l'historique puis retirés.
  - Réception : ne crée plus de facture automatiquement ; elle alimente la liste « à facturer ». Option paramétrable `module_parameters('ap','auto_invoice_on_receipt')` pour les achats comptoir (G-D6-18).
  - Écran : `InvoiceFromReceiptsModal` (sélection des BR ouverts du fournisseur, cases par ligne, quantité proposée = reçu − facturé, prix proposé = prix BR) ; dans `PODetailModal` une section « Réceptions / facturé » par ligne (`odoo-table` 4 colonnes commandé / reçu / facturé / reste).
- **Reprise** : pour les 294 factures BC existantes, `invoice_items.receipt_item_id` par appariement (BC, article) quand unique (Q20 : 754/816 lignes ont une RVI correspondante) ; les 62 lignes sans RVI restent NULL (flag « legacy »).
- **Effort** : L. **Dépendances** : G-D6-01, G-D6-08 ; D5 (RVI doit porter le prix et le contenant). **Risques** : les BC `IMPORT-` et les éditions admin (W-10, 2 BC `livre_complet` sans BR) n'ont pas de RVI → ces lignes ne peuvent pas être facturées « depuis réception » ; prévoir la saisie libre avec `po_line_id` seul.

### G-D6-03 — La fusion de factures supprime physiquement des factures et laisse le grand livre faux

- **Capacités / faiblesses** : C-D6-02, C-D6-07 ; W-19, W-27.
- **Preuve** : `mergeForPurchaseOrders` (`server/src/repositories/accounting.repository.ts:767-920`) : pré-crée une facture pour **chaque** BC y compris partiel (`:786-789`, via `createInvoiceFromPo` sur `quantity_delivered`), déplace les lignes (`:836-840`), recalcule `amount`/`tax_amount` du maître (`:843-875`), écrase `reception_vouchers.supplier_invoice_number` (`:890-897`), puis `DELETE FROM invoices WHERE id = ANY($1)` (`:898-905`). Aucune occurrence de `regenerateInvoiceEntry`/`reverseEntriesForSource`/`FLAGS` entre les lignes 767 et 920 (grep). Base : 35 lignes `invoice_purchase_orders`, 1 facture à 2 BC.
- **Manque vs standard** : aucun ERP ne fusionne des pièces comptabilisées ; on crée **une** facture depuis N réceptions (G-D6-02). Une pièce existante ne disparaît jamais (P15) : annulation tracée + contre-écriture.
- **Impact métier** : avec `LEDGER_AUTOGEN` actif, écritures 4411 fantômes des factures supprimées et maître à l'ancien montant → solde fournisseur, TVA déductible et réconciliation `v_reconciliation_check` faux ; numéros `FR-` réattribués (`generateInvoiceNumber` = `COUNT(*)+1`).
- **Priorité** : **P0** (intégrité financière).
- **Conception cible** : retirer `POST /invoices/merge` et `MergeInvoicesModal` (`PurchaseOrdersTab.tsx:1580-1660`) une fois G-D6-02 livré. Transitoire (si G-D6-02 est lotissé plus tard) : la fusion devient `cancel` tracé des factures absorbées (`validation_status='cancelled'`, `cancelled_by/at/reason='merged_into:<id>'`) + `regenerateInvoiceEntry` du maître dans la même transaction + refus si l'une est `posted` en période close. Interdire la pré-création sur BC partiel (`:780-789`).
- **Reprise** : aucune (les factures déjà supprimées sont perdues) ; lancer `cleanup-orphan-entries.ts` en mode diagnostic pour les 10 écritures orphelines (W-25).
- **Effort** : S (transitoire) / inclus dans G-D6-02. **Risques** : aucun.

### G-D6-04 — Aucune politique de facturation par ligne (ordered / received) ni lien ligne facture → ligne BC

- **Capacités / faiblesses** : C-D6-03 ; W-15 (partie), W-44.
- **Preuve** : `\d invoice_items` (schema_d.txt:166-190) : colonnes `product_id, ingredient_id, packaging_id, description, quantity, unit_price, subtotal, tva_*, category_id` — pas de `purchase_order_item_id` ; `\d purchase_order_items` : pas de `bill_policy`/`match_level`/`quantity_invoiced` ; `expense_categories` (Q24) : `requires_po` mais pas de politique de facturation ; `createInvoiceFromPo:101-116` lit `quantity_delivered` par article du BC (pas par ligne de réception). Q20 : 9 lignes facture dont la quantité ≠ reçu ; Q21 : 5 lignes à prix ≠ BC (762 comparables) — sans qu'aucun écran ne le montre.
- **Manque vs standard** : Odoo `purchase_method ∈ {purchase, receive}` par article, SAP GR-based IV, Oracle `match_option`. La ligne de facture sait de quelle ligne de BC et de quelle réception elle vient ; `qty_to_invoice` est calculée, pas re-saisie.
- **Impact métier** : impossible de savoir quelle livraison est facturée quand le fournisseur facture au mois (Ecomab) ; les charges (loyer, énergie) et services passent nécessairement hors BC puisque le BC n'accepte que des articles de stock (CHECK `po_item_kind_check`).
- **Priorité** : **P1**.
