## 0. Lecture rapide

La réception est aujourd'hui **un seul appel** (`POST /purchase-orders/:id/confirm-delivery` → `receptionVoucherRepository.create`, `server/src/repositories/reception-voucher.repository.ts:284-555`) qui fait tout dans une transaction : BR + lignes + lot + stock + statut BC + DA + facture + écriture. C'est la force du module (atomicité, routage ingrédient/consommable, saisie par contenant, garde anti-doublon de facture fournisseur). Mais ce qu'il écrit n'est **ni immuable, ni contrôlé, ni identifiable** :

- le stock est compté **deux fois** à chaque réception (trigger `trg_inventory_sync_lots` + `UPDATE inventory … + $1`, l.431-459) → 176/377 lignes `inventory` fausses, 116 exactement égales à la dernière réception ;
- 634/669 lots n'ont **pas de numéro**, 389/401 lots actifs avec stock n'ont **pas de DLC** → rappel ONSSA et FEFO impossibles ;
- la sur-livraison n'est **pas bornée** (12 lignes, 0,0035 kg commandé → 5 kg reçus), le prix saisi **écrase** le prix du BC et le catalogue, `forceComplete` **réécrit** la commande d'origine ;
- l'annulation **supprime physiquement** BR, lignes, lots, mouvements et facture (l.666-745) et le numéro BR est réattribuable ; aucune correction de ligne n'existe ;
- retour fournisseur, avoir attendu, casse à la réception, contrôle qualité, poids pesé, attendus du jour, écran/PDF de BR, réception par le magasinier : **absents ou morts** (table `reception_quality_checks` à 0 ligne, 4 routes `/reception-vouchers` jamais appelées).

21 écarts identifiés : **8 P0, 8 P1, 4 P2, 1 P3**.

## 2. Socle cible commun aux fiches (pour ne pas le répéter)

Les 21 fiches s'appuient sur un même modèle cible, dérivé des patterns P1 (journal append-only), P3 (double unité figée), P5 (tolérances), P10/P15 (audit, jamais de suppression). Analogie Oracle : le BR devient un bloc maître/détail dont le **détail est une table de transactions** (comme `RCV_TRANSACTIONS`) ; les compteurs du BC sont des colonnes entretenues par un **unique trigger `AFTER INSERT`**, jamais par du code applicatif.

```
reception_vouchers (en-tête, réutilisée)
  + voucher_kind      text NOT NULL DEFAULT 'receipt'   CHECK (voucher_kind IN ('receipt','return','reversal'))
  + status            text NOT NULL DEFAULT 'posted'    CHECK (status IN ('draft','posted','reversed'))
  + received_at       timestamptz NOT NULL DEFAULT now()        -- date/heure réelle saisissable
  + supplier_delivery_note_no text, carrier text
  + zone              text NOT NULL DEFAULT 'economat'  CHECK (zone IN ('economat','pesage','quai'))
  + reverses_voucher_id uuid REFERENCES reception_vouchers(id)  -- voucher miroir
  + reversed_by uuid, reversed_at timestamptz, reverse_reason_code text
  + posted_by uuid, posted_at timestamptz, updated_at timestamptz
  + remainder_action  text CHECK (remainder_action IN ('keep','cancel'))  -- choix explicite à chaque partiel
  voucher_number : séquence par (type, année) sans trou, attribuée au passage draft → posted (P13)

reception_voucher_items (détail = journal immuable, réutilisée)
  + kind              text NOT NULL DEFAULT 'receive'
                      CHECK (kind IN ('receive','correct_up','correct_down','reject','return','scrap'))
  + parent_item_id    uuid REFERENCES reception_voucher_items(id)   -- correct/return → ligne d'origine
  + qty_container     numeric(12,3), qty_per_container numeric(12,4)  -- snapshot (P3)
    quantity_received reste la quantité en unité de base (> 0)
  + signed_qty_base   numeric(12,4) GENERATED ALWAYS AS
                      (quantity_received * CASE WHEN kind IN ('receive','correct_up') THEN 1 ELSE -1 END) STORED
  + po_unit_price     numeric(12,4)        -- prix BC figé au moment de la réception (accrual)
  + qty_base_weighed  numeric(14,4), weighing_source text, weight_variance numeric(14,4) GENERATED
  + weight_decision   text CHECK (… IN ('accepted','accepted_with_reserve','partial_reject','dispute'))
  + reason_code       text REFERENCES ref_entries(code)  -- obligatoire si kind <> 'receive'
  + lot_id            uuid REFERENCES ingredient_lots(id)  -- pour return/correct_down/scrap
  + to_refund boolean, return_action text CHECK (… IN ('credit','replace','scrap'))
  + created_by uuid NOT NULL
  trigger trg_rvi_immutable : BEFORE UPDATE OR DELETE → RAISE, sauf UPDATE de notes/category_id
  trigger trg_rvi_after_insert : recalcule purchase_order_items.quantity_delivered = Σ signed_qty_base
                                  (kind <> 'reject'), delivery_completed, et insère po_line_events (D4)

ingredient_lots (réutilisée)
  lot_number NOT NULL UNIQUE (restauré) = 'LI-' || to_char(received_at,'YYMMDD') || '-' || lpad(nextval('lot_number_seq'))
  + status CHECK étendu : ('quarantine','active','blocked','depleted','expired','waste','returned')
  + status_reason_code text, status_changed_by uuid, status_changed_at timestamptz
  + supplier_lot_number, expiration_date, manufactured_date : NOT NULL conditionnel par catégorie (trigger)
  + received_at timestamptz (aujourd'hui date) : copie de reception_vouchers.received_at

Référentiels (P14) : expense_categories + requires_lot bool, requires_dlc bool, min_shelf_life_days int,
                     receipt_routing text ('direct'|'inspection') ; surcharge par ingredients.*
                     reason codes = ref_tables('reception_reason_codes') / ref_entries (module référentiel mig 058)
                     module_parameters(module, key, value jsonb, updated_by, updated_at)  -- nouveau, 1 table

Une seule écriture de stock : INSERT ingredient_lots (trigger mig 114 → inventory) + INSERT inventory_transactions(ingredient_lot_id)
                              / packagingItemRepository.adjustStock pour les consommables. Plus aucun UPDATE inventory applicatif.
```

Chemin unique d'entrée : `POST /receptions` (remplace `confirm-delivery`, `POST /reception-vouchers`, `POST /inventory/restock`). Rôle **WAREHOUSE** (magasinier, manager, admin), prix masqués pour le magasinier. Écrans : `client/src/features/stock/ReceptionsPage.tsx` (onglet Réceptions de l'Économat, ui-timeline « Attendu → Saisi → Contrôlé → En stock », odoo-table, StatusBanner), `ReceptionForm.tsx`, `ReceptionDetail.tsx`, `ReturnModal.tsx`, `QualityCheckPanel.tsx` ; dans Achats, `PODetailModal` affiche la liste des BR (smart button) et perd `DeliveryModal`.

## 3. Fiches d'écart

### G-D5-01 — Réception référencée : pas d'attendus du jour, date réelle non saisissable, pas de n° BL, aucun écran ni document BR

- **Capacités** : C-D5-01 (essentiel). **Faiblesses** : W-47, W-67, W-08 (partie), W-66.
- **Statut** : partiel.
- **Preuves** :
  - `reception-voucher.repository.ts:345-351` : `INSERT INTO reception_vouchers (voucher_number, purchase_order_id, notes, received_by, store_id, supplier_invoice_number, supplier_invoice_date)` — `reception_date` n'est jamais fourni → `DEFAULT CURRENT_DATE` (`schema_d.txt` l.63). SQL : `SELECT COUNT(*) FROM reception_vouchers WHERE reception_date <> created_at::date` → **0 / 307**. Le lot hérite `received_at = CURRENT_DATE` (`:434`).
  - `purchase-order.controller.ts:76-102` (`confirmDelivery`) ne lit ni date, ni n° BL, ni zone dans `req.body` (`:84`).
  - Aucune liste des attendus : `findOverdue` (`purchase-order.repository.ts:531-541`) exige `expected_delivery_date IS NOT NULL` (101 BC ignorés d'après 01_existant) et ne renvoie pas le reliquat par ligne ; le magasinier n'a aucune route (`purchase-order.routes.ts` : tout en `ADMIN_MANAGER`).
  - Aucun écran BR : `grep -rn receptionVouchersApi client/src/features` → 0 (API définie `client/src/api/purchase-orders.api.ts:48-57`) ; `PODetailModal` montre le cumul livré, pas les BR. Aucun PDF : `ls server/src/services | grep -i pdf` → `invoice-pdf`, `purchase-order-pdf`, `recipe-fiche-pdf`. Le numéro `BR-YYYY-NNNN` n'apparaît que sur la fiche lot (`client/src/features/stock/IngredientDetailPage.tsx:925-927`).
  - Usage : 259/298 premiers BR < 10 min après le BC (SQL §18 de `d5_verif.sql`) — la réception est saisie a posteriori par le manager, pas par celui qui réceptionne.
- **Manque vs standard ERP** : SAP MIGO, Oracle « Receive Expected Shipments », Odoo `stock.picking` IN partent tous d'une **liste des attendus** (BC envoyés avec reliquat par ligne), proposent le reliquat, exigent la **date réelle** et le **n° de BL** du fournisseur, et produisent un document imprimable numéroté.
- **Impact métier** : les délais fournisseur sont faux (dates = dates de frappe), aucune preuve de réception signable, impossible de retrouver « ce qu'on attend demain », BR invisibles en cas de litige avec Ecomab/OVOTEC/MAGHREBLAC (70 % de la dépense).
- **Priorité** : **P1**.
- **Conception cible** :
  - DDL (mig 310) : `reception_vouchers` + `received_at timestamptz NOT NULL DEFAULT now()`, `supplier_delivery_note_no varchar(100)`, `carrier varchar(100)`, `zone text NOT NULL DEFAULT 'economat'`, `posted_by uuid`, `posted_at timestamptz`, `updated_at timestamptz` ; `reception_date` conservée comme colonne générée `(received_at AT TIME ZONE 'Africa/Casablanca')::date` pour les requêtes existantes (`findAll`, index `idx_rv_date`). Index `idx_rv_received_at (received_at DESC)`. Contrainte : `received_at <= now() + interval '1 day'` et `received_at >= po.order_date` (trigger, avertissement non bloquant via `reason_code 'backdated'`).
  - Vue `v_expected_receipts` : lignes BC `status IN ('envoye','livre_partiel')` × `remaining = quantity_ordered − quantity_delivered − quantity_cancelled > 0`, avec `expected_delivery_date`, `days_late`, fournisseur, contenant, **sans prix**.
  - Endpoints : `GET /receptions/expected?date=&supplierId=` (WAREHOUSE ; omet `unit_price` si rôle = magasinier) ; `GET /receptions?from&to&supplierId&status` (WAREHOUSE lecture, paginé) ; `GET /receptions/:id` (en-tête + journal des lignes + lots + contrôles) ; `GET /receptions/:id/pdf` (service `reception-voucher-pdf.service.ts` sur le modèle de `purchase-order-pdf.service.ts`, identité société depuis `company_settings`, logo data URI — mémoire « Uploads Cloud Run »). `POST /receptions` : voir G-D5-21 pour le contrat et les gardes.
  - Écran : `client/src/features/stock/ReceptionsPage.tsx` sous l'Économat (navigation `stock`, rôle WAREHOUSE) : barre ui-timeline (Attendu → Saisi → Contrôlé → En stock) qui filtre, odoo-table des attendus (fournisseur, BC, article, reste à recevoir en contenants et en base, date prévue, retard), StatusBanner « 3 BC en retard » ; bouton `odoo-btn-primary` « Réceptionner » ouvre `ReceptionForm` (date/heure réelle pré-remplie `now()`, n° BL, zone, lignes). `ReceptionDetail` affiche le journal (kind, qty, lot, DLC, auteur, heure) et les boutons Corriger / Retour / Extourner / PDF selon rôle. Dans `PurchaseOrdersTab`, `PODetailModal` reçoit un onglet « Réceptions (n) » listant les BR (`GET /receptions?purchaseOrderId=`).
  - Règles : un BR `posted` n'est plus modifiable (G-D5-02) ; `supplier_delivery_note_no` unique par fournisseur (index partiel) avec avertissement, pas blocage (un BL peut être livré en deux fois).
- **Backfill** : `received_at = created_at` pour les 307 BR ; `posted_by = received_by`, `posted_at = created_at` ; `zone = 'economat'`.
- **Effort** : **M** (serveur S, PDF S, écran M). **Dépendances** : G-D5-12 (rôle), G-D5-21 (contrat `POST /receptions`). **Risques** : la `DeliveryModal` reste utilisée par le manager tant que l'écran Économat n'est pas livré — garder les deux pendant une version, puis retirer `confirm-delivery`.
