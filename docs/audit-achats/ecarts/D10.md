### G-D10-01 — Permissions par action et séparation des tâches (SoD) : tout le cycle est entre les mains d'un seul rôle

- **Capacités** : C-D10-01 (socle, essentiel) ; touche C-D3-02 (approbation), C-D6-07, C-D7-05. **Faiblesses** : W-28, W-54, W-48 (partie), W-10 (édition admin du stock), T-W4, T-W11.
- **Preuve** :
  - `server/src/middleware/role.middleware.ts:5-19` : `authorize(...roles)` = `roles.includes(req.user.role)`. Aucune notion d'action, de module, de plafond ni de propriétaire.
  - `shared/src/constants/roles.ts:21-40` : 9 rôles (admin, manager, cashier, baker, pastry_chef, viennoiserie, beldi_sale, saleswoman, magasinier). Aucun rôle acheteur / approbateur / comptable fournisseurs / trésorier / auditeur.
  - `server/src/routes/purchase-order.routes.ts:9-28`, `reception-voucher.routes.ts:9-12`, `accounting.routes.ts:59-111` : création BC, envoi, réception, édition des lignes livrées, facture, statut manuel `paid`, paiement, suppression de paiement = **le même groupe `ADMIN_MANAGER`**. Seuls `cancel-reception`, `DELETE /purchase-orders/:id`, `DELETE /suppliers/:id`, `unmark-cashed` sont `ADMIN`.
  - `permissionRepository` (grille `user_permissions.can_create/can_edit/can_delete`) n'est lu que par `server/src/controllers/user.controller.ts:4,155,169,194` — aucun endpoint métier ne la consulte ; côté client `usePermissions().canCreate/canEdit/canDelete` existe (`client/src/context/PermissionsContext.tsx:9-13,78-87`) et n'est utilisé par aucun écran achats (grep sur les 3 fichiers → 0).
  - `accounting.controller.ts:384-397` (`PUT /invoices/:id/status` autorise `paid` sans paiement) ; `:668` `const ENFORCE_PO_REQUIREMENT = false` ; `:736-739` `DELETE /payments/:id` sans contrôle ; `purchase-order.controller.ts:206-250` + `purchase-order.repository.ts:506-527` (`quantity_delivered` libre → stock sans BR).
  - SQL (lecture seule) : `SELECT count(*) FROM purchase_orders po JOIN reception_vouchers rv ON rv.purchase_order_id=po.id JOIN invoices i ON i.purchase_order_id=po.id JOIN payments p ON p.invoice_id=i.id WHERE po.created_by=rv.received_by AND rv.received_by=p.created_by` → **256** chaînes BC→BR→facture→paiement réalisées par une seule et même personne ; `274/289` paiements créés par le créateur de la facture ; `users GROUP BY role` : admin 3, manager 1, cashier 4 (2 actifs), pastry_chef 1, **magasinier 0**.
  - `user_permissions` : module `purchasing` 1 ligne (create/edit/delete = 1), `accounting` 1 ligne — la grille existe mais ne cloisonne rien.
- **Manque vs standard** : SAP C66 / ORA D10.1 / ODOO groupes + record rules : permissions par **action** (`po.approve`, `po.receive`, `invoice.release_hold`, `payment.execute`, `supplier.bank.approve`), rôles métier distincts, règles d'incompatibilité (`approver ≠ creator`, `payer ≠ invoice_creator`) vérifiées au runtime, cumul tracé, filtrage des colonnes sensibles (le magasinier ne voit pas `unit_price`), auditeur lecture seule.
- **Impact** : aucun contrôle interne — une facture peut être soldée sans paiement, un paiement supprimé, du stock créé sans réception, par le même utilisateur qui a tout saisi (c'est le cas pour 256 BC). Le gérant est aussi celui qui corrige : aucune revue croisée. Pour un expert-comptable ou un contrôle fiscal (CGI art. 145/146), la pièce n'est pas probante. Dette bloquante pour le plan SaaS (plusieurs gérants, plusieurs magasins).
- **Priorité** : **P0** (contrôle financier).
- **Conception cible** (adaptée à 2-3 personnes : la SoD n'est pas « impossible » mais « tracée et plafonnée », comme Odoo avec 2 utilisateurs) :
  - DDL (mig 304) :
    ```sql
    CREATE TABLE app_actions (code text PRIMARY KEY, module text NOT NULL, label text NOT NULL, sensitive boolean NOT NULL DEFAULT false);
    -- jeu initial achats : pr.create, pr.cancel, po.create, po.edit_draft, po.submit, po.approve, po.send, po.cancel, po.final_close,
    --   gr.receive, gr.cancel, gr.quality, gr.return, inv.create, inv.edit, inv.validate, inv.hold_release, inv.cancel,
    --   pay.create, pay.cash, pay.cancel, supplier.edit, supplier.bank.approve, supplier.price.edit, stock.adjust, audit.read
    CREATE TABLE role_actions (role text NOT NULL, action_code text NOT NULL REFERENCES app_actions(code), amount_limit numeric(12,2),
      PRIMARY KEY (role, action_code));
    CREATE TABLE user_action_overrides (user_id uuid REFERENCES users(id), action_code text REFERENCES app_actions(code),
      granted boolean NOT NULL, amount_limit numeric(12,2), granted_by uuid REFERENCES users(id), granted_at timestamptz DEFAULT now(),
      PRIMARY KEY (user_id, action_code));
    CREATE TABLE sod_rules (action_a text REFERENCES app_actions(code), action_b text REFERENCES app_actions(code),
      mode text NOT NULL CHECK (mode IN ('block','warn')), PRIMARY KEY (action_a, action_b));
    -- ex. ('po.create','po.approve','block'), ('inv.validate','pay.create','warn'), ('gr.receive','inv.validate','warn')
    ```
    Rôles ajoutés dans `shared/src/constants/roles.ts` : `buyer` (acheteur), `ap_clerk` (comptable fournisseurs), `auditor` (lecture seule) ; le `magasinier` reçoit `gr.receive/gr.quality/gr.return` sans `*.price.*` (cf. G-D10-02). `admin` conserve tout mais **tracé**.
  - Runtime : nouveau middleware `requireAction('po.approve')` (`server/src/middleware/action.middleware.ts`) qui lit `role_actions ∪ user_action_overrides` (cache 60 s invalidé par `PUT /users/:id/permissions`) puis, pour les actions `sensitive`, appelle `fn_sod_check(user_id, action_code, document_type, document_id)` : la fonction lit `document_actions` (G-D10-03) pour savoir qui a fait l'action incompatible sur ce document ; `block` → 403 `SOD_VIOLATION`, `warn` → autorisé mais `document_actions.sod_override = true` + notification admin (G-D10-06). Analogie Forms : c'est un `WHEN-VALIDATE-RECORD` côté serveur alimenté par une table de règles, pas du code.
  - Plafonds : `amount_limit` sur `po.approve` / `pay.create` (ex. manager 20 000 MAD, au-delà admin) — remplace l'absence de circuit d'approbation (D3) par un garde-fou minimal.
  - Filtrage de colonnes : `purchaseOrderRepository.findById(id, { withPrices: can('po.price.view') })` ; le DTO magasinier n'inclut pas `unit_price`/`total`.
  - Endpoints : `GET /me/actions` (liste des actions effectives, consommée par `PermissionsContext`) ; `GET /users/:id/actions`, `PUT /users/:id/actions` (admin) ; `GET /documents/:type/:id/allowed-actions` (sert le `StatusBanner`, G-D10-12).
  - Écrans : page « Utilisateurs → Permissions » étendue en `odoo-table` actions × rôles avec plafond ; chaque bouton achats passe par `allowedActions` du serveur (plus de `isAdmin = role === 'admin'` dans `PurchaseOrdersTab.tsx:105`).
  - Règles : (1) supprimer `PUT /invoices/:id/status` → `paid` (statut dérivé des paiements, P11) ; (2) `DELETE /payments/:id` → `POST /payments/:id/cancel` (G-D10-04) ; (3) `replaceItems` ne touche plus `quantity_delivered` (D4/D5) ; (4) `POST /purchase-requests` limité aux rôles PRODUCTION + WAREHOUSE (plus le caissier).
- **Reprise** : seed `role_actions` reproduisant l'état actuel (admin/manager = tout) pour ne rien casser le jour 1 ; puis activation des `sod_rules` en mode `warn` pendant 1 mois, `block` ensuite. Aucune donnée à migrer.
- **Effort** : **M** (middleware + 4 tables + écran permissions ; la refonte bouton par bouton se fait dans G-D10-12).
- **Dépendances** : G-D10-03 (`document_actions` pour la SoD runtime), G-D10-06 (alerte `warn`). Doit précéder la refonte D3 (approbation) et D7 (paiements).
- **Risques** : équipe de 2-3 personnes → trop de `block` paralyse ; commencer par `warn` + plafonds. Les utilisateurs `admin` multiples (3) doivent être revus : un seul admin technique, les autres en `manager`/`buyer`.

    CREATE OR REPLACE FUNCTION fn_trace_downstream(p_lot uuid) RETURNS TABLE(level int, node_type text, node_id uuid, label text, qty numeric, at timestamptz) LANGUAGE sql STABLE AS $$
      WITH RECURSIVE t AS (
        SELECT 0 AS level, 'ingredient_lot'::text AS node_type, p_lot AS node_id
        UNION ALL
        SELECT t.level+1, x.node_type, x.node_id FROM t JOIN LATERAL (
          SELECT 'production_plan' AS node_type, plu.production_plan_id AS node_id FROM production_lot_usage plu WHERE t.node_type='ingredient_lot' AND plu.ingredient_lot_id=t.node_id

          UNION ALL SELECT 'order_item', oi.id FROM order_items oi WHERE t.node_type='product_lot' AND oi.product_lot_id=t.node_id
        ) x ON true WHERE t.level < 6)
      SELECT level, node_type, node_id, NULL::text, NULL::numeric, NULL::timestamptz FROM t $$;
