# D7 — Paiements & trésorerie fournisseurs : analyse d'écarts et conception cible

Date : 2026-10-12. Dépôt `/Users/anissbouida/projets/Ofauria-app` (working tree, HEAD `cb91fc3`), base locale 5433 en lecture seule (`_migrations` max 303). Toute affirmation sur le code est référencée `fichier:ligne` (vérifiée ce jour) ; toute affirmation sur les données est accompagnée de la requête SQL exécutée.

Lecture pour un ancien développeur Oracle Forms : `payments` est aujourd'hui l'équivalent d'un bloc `AP_INVOICE_PAYMENTS` à une seule ligne par facture, sans `AP_PAYMENT_SCHEDULES` alimenté, sans `AP_INVOICE_PAYMENT_APPLICATIONS` et sans statut de pièce. La cible décrite ici recrée ces trois objets en PostgreSQL (tables + triggers = « packages » côté base) et ne touche à `invoices.paid_amount` que par un seul trigger.

## 0. Résumé

- **17 écarts** : 5 P0, 6 P1, 6 P2, 0 P3. Les P0 sont tous de contrôle financier ou de conformité CGI (mode de paiement typé, compteur espèces 5 000 / 50 000 MAD, blocages et statut de paiement, annulation tracée au lieu de `DELETE`, virements internes passés en charges).
- Le socle existant à préserver est réel : `paymentRepository.create` (verrou `FOR UPDATE`, garde sur-paiement, doublon de chèque, `paid_amount` resynchronisé dans la même transaction, 0 dérive sur 317 factures), la distinction émission / encaissement des chèques et traites (`cashed_at`, 5111/4415 → 5141), le modèle `scheduled_payments` de la mig 258 (sain mais vide) et le rapprochement bancaire minimal (`bank_statements`).
- Le compteur espèces est aujourd'hui **impossible à calculer** : 281 paiements `expense` en espèces (241 104 DH) n'ont aucun `supplier_id`, et 106 000 DH de « Virement bancaire » sont enregistrés comme dépenses en espèces. Deux dépassements journaliers > 5 000 DH existent déjà sur les seules factures liées à un tiers (BS2M 5 520 DH le 15/07 ; Abdelilah 5 221 DH en 6 paiements le 31/07 = fractionnement).

### G-D7-01 — Conditions de paiement fournisseur et échéancier généré à la validation de la facture

- **Capacités / faiblesses** : C-D7-01 (essentiel) ; W-18, W-31 ; lien C-D1-01 (fiche fournisseur), C-D6-07 (validation facture).
- **Statut** : absent.
- **Preuves**
  - `\d suppliers` : `name, contact_name, phone, email, address, city, ice, notes, is_active, created_at` — aucune condition de paiement, aucun délai. Formulaire fournisseur à 8 champs : `client/src/features/purchasing/PurchasingPage.tsx:347-365`.
  - La facture auto créée à la réception n'a ni `due_date` ni mode : `server/src/repositories/reception-voucher.repository.ts:168-176` (INSERT sans `due_date`).
  - `SELECT count(*), count(due_date), count(expected_payment_mode) FROM invoices WHERE invoice_type='received'` → `317 | 34 | 88` ; sur les ouvertes : `SELECT count(*), count(due_date) FROM invoices WHERE invoice_type='received' AND status NOT IN ('paid','cancelled')` → `37 | 0`.
  - `PUT /invoices/:id/payment-terms` existe (`server/src/controllers/accounting.controller.ts:368-383`, `accounting.repository.ts:1032-1051`) mais `invoicesApi.updatePaymentTerms` (`client/src/api/accounting.api.ts:75`) n'a aucun appelant : mort.
  - Le vrai délai de paiement est aujourd'hui porté par le chèque/la traite : `SELECT payment_method, avg(check_date-payment_date) …` → chèque 31,1 j (10-62), traite 52,9 j (−2 à 96) ; 139 k DH sur 230 k payés.
- **Manque vs standard ERP** : dans SAP (ZTERM), Oracle (`AP_PAYMENT_SCHEDULES`), Odoo (`payment.term`), la facture reçoit à sa validation un échéancier dérivé des conditions du fournisseur (jours nets, fin de mois, échelonné). Ici la date est optionnelle, saisie à la main, jamais posée par le flux principal (294/317 factures auto).
- **Impact boulangerie** : 89 546 DH d'encours (28 % du facturé) sans date ; impossible de savoir ce qui est dû à Ecomab (35,6 k, 11 factures de juillet) cette semaine ; les retards ne se déclenchent jamais (voir G-D7-10/15) ; les grands comptes (Ecomab, OVOTEC, MAGHREBLAC, RICA) travaillent à 30/60 j par traite — ce délai contractuel n'est écrit nulle part.
- **Priorité** : **P1** (standard ERP absent, coûte du temps chaque semaine ; devient prérequis des P0 G-D7-07 et des P1 G-D7-10).
- **Conception cible**
  - Table de règles (P14) :
    ```sql
    -- mig 304_payment_terms.sql
    CREATE TABLE payment_terms (
      id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
      code varchar(20) NOT NULL UNIQUE,            -- 'COMPTANT', 'NET30', 'FDM30', '3X30'
      label varchar(100) NOT NULL,
      method varchar(20) NOT NULL CHECK (method IN ('net','cod','end_of_month','day_of_month')),
      days int NOT NULL DEFAULT 0 CHECK (days >= 0),
      day_of_month smallint CHECK (day_of_month BETWEEN 1 AND 31),
      installments jsonb NOT NULL DEFAULT '[]',     -- [{"pct":50,"days":0},{"pct":50,"days":30}] ; vide = 1 échéance
      discount_pct numeric(5,2), discount_days int, -- escompte : colonnes prévues, pas d'écran
      is_active boolean NOT NULL DEFAULT true,
      created_at timestamptz NOT NULL DEFAULT now(), updated_at timestamptz
    );
    CREATE FUNCTION fn_due_date(p_term uuid, p_base date) RETURNS date LANGUAGE sql STABLE AS $$
      SELECT CASE t.method
        WHEN 'cod' THEN p_base
        WHEN 'net' THEN p_base + t.days
        WHEN 'end_of_month' THEN (date_trunc('month', p_base + t.days) + interval '1 month - 1 day')::date
        WHEN 'day_of_month' THEN LEAST(
             (date_trunc('month', p_base + t.days) + interval '1 month')::date + (t.day_of_month - 1),
             (date_trunc('month', p_base + t.days) + interval '2 month - 1 day')::date)
      END FROM payment_terms t WHERE t.id = p_term $$;   -- équivalent PKG_ECHEANCES.DATE_ECHEANCE
    ALTER TABLE suppliers ADD COLUMN payment_term_id uuid REFERENCES payment_terms(id),
                          ADD COLUMN default_payment_mode varchar(20);   -- cf. G-D7-03
    ALTER TABLE invoices  ADD COLUMN payment_term_id uuid REFERENCES payment_terms(id),   -- COPIÉ à la création
                          ADD COLUMN payment_base_date date;             -- date de départ (facture ou réception)

Idempotente : `UNIQUE (invoice_id, installment_no)`.
  - Règle : conditions **copiées** sur la facture (modifier le fournisseur ne réécrit pas les factures existantes) ; recalcul autorisé tant qu'aucune `payment_application` active ne cible l'échéancier (règle déjà codée `payment-schedule.repository.ts:179-192`, à conserver).
  - Endpoints : `GET/POST/PUT /payment-terms` (admin) ; `PUT /suppliers/:id` accepte `paymentTermId`, `defaultPaymentMode` ; `POST /invoices/:id/validate` génère l'échéancier ; `POST /invoices/:id/schedule` (existant) reste pour l'échelonnement manuel d'une facture déjà validée ; `GET /invoices/:id/schedule` (= `GET /payment-schedules/by-source/invoice/:id`, à brancher au lieu de le supprimer).
  - Écrans : fiche fournisseur (onglet « Conditions ») : terme, mode par défaut, RIB (G-D7-03) ; page facture : bloc « Échéancier » en `odoo-table` (n°, date, dû, réglé, reste, hold) sous la `ui-timeline` reçue → validée → payée ; référentiel « Conditions de paiement » dans Paramètres (`odoo-table` éditable, même pattern que `container_types`, mig 225).

### G-D7-02 — Lettrage N:N (`payment_applications`) : un paiement pour N échéances / N factures, avoirs et acomptes, dé-lettrage tracé

- **Capacités / faiblesses** : C-D7-02 (essentiel) ; W-50, W-20, W-34 (partie lettrage) ; patterns P11, P12.
- **Statut** : partiel / défaillant.
- **Preuves**
  - Modèle 1:1 : `payments.invoice_id` FK directe ; `paymentRepository.create` verrouille **une** facture (`server/src/repositories/accounting.repository.ts:1932-1945`), garde sur-paiement sur cette seule facture (`:1958-1969`), resync `updatePaidAmount` de cette seule facture (`:2060`).
  - Chèque multi-factures = N lignes `payments` portant le même `check_number` : `SELECT count(*) FILTER (WHERE n>1), sum(n) FILTER (WHERE n>1) FROM (SELECT check_number, count(*) n FROM payments WHERE check_number IS NOT NULL GROUP BY 1) x` → **9 chèques, 30 lignes** ; un même chèque saisi « AAA 5100009 » et « AAA  5100009 » (rapport FA §10.3) ; regroupement côté client par normalisation (`client/src/features/accounting/AccountingPage.tsx:3128`) ; encaissement en `Promise.all` non atomique (`:2973`, `:2993`).
  - Avoir = pseudo-paiement `payment_method='avoir'` créé uniquement dans le flux chèque/traite (`accounting.repository.ts:1990-2011`), comptabilisé `4411 D / 5161 C` (`journal-generator.service.ts:508-509`, écriture CA-2026-00438, W-20) ; `SELECT count(*), sum(amount) FROM payments WHERE payment_method='avoir'` → 1, 1 200 DH.
  - Lettrage comptable tout-ou-rien : `autoLettrer` ne pose `lettrage_id` que si Σ débits = Σ crédits des lignes 4411 de la facture et de ses paiements (`journal-generator.service.ts:746-787`, test `:769-772`) ; `SELECT count(*) FILTER (WHERE lettrage_id IS NULL), count(*) FROM journal_entry_lines jel JOIN accounts a … WHERE a.code LIKE '4411%' AND je.status='posted'` → **517 / 564 non lettrées**, solde −51 826,66 DH.
  - Paiement partiel autorisé (6 factures à 2 paiements) mais aucune trace de « quelle échéance » est réglée ; `payments.scheduled_payment_id` 0/689.
  - Dé-lettrage = suppression physique du paiement (`:2109-2140`) ; aucun `reversed_at`.
- **Manque vs standard ERP** : Oracle `AP_INVOICE_PAYMENTS` / D365 `VendSettlement` / NetSuite applications / Odoo `account.partial.reconcile` : la pièce de règlement est indépendante des factures, une table d'application porte `(paiement, échéance, montant, escompte, écart passé en charge)` ; avoirs et acomptes s'appliquent par le même mécanisme ; le solde facture est dérivé.
- **Impact boulangerie** : un chèque de 19 623 DH à Ecomab couvrant 5 factures se saisit 5 fois (5 risques d'erreur de montant, 5 encaissements à confirmer) ; un avoir fournisseur ne peut pas être conservé pour une facture future ; impossible de régler « 10 000 DH sur compte » à OVOTEC sans choisir une facture ; l'auxiliaire 4411 ne peut pas produire de balance âgée fiable (517 lignes non lettrées).
- **Priorité** : **P1**.
- **Conception cible**
  ```sql
  -- mig 305_payment_applications.sql
  CREATE TABLE payment_applications (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    source_type varchar(20) NOT NULL CHECK (source_type IN ('payment','credit_note','prepayment')),
    source_id uuid NOT NULL,                              -- payments.id | supplier_credit_notes.id (C-D6-09) | supplier_prepayments.id
    scheduled_payment_id uuid NOT NULL REFERENCES scheduled_payments(id),
    invoice_id uuid NOT NULL REFERENCES invoices(id),     -- dénormalisé = scheduled_payments.invoice_id (CHECK par trigger)
    amount numeric(14,2) NOT NULL CHECK (amount > 0),
    discount_taken numeric(14,2) NOT NULL DEFAULT 0,
    write_off numeric(14,2) NOT NULL DEFAULT 0,           -- petit écart de règlement (≤ paramètre, ex. 5 DH) → 6581/7581
    applied_at timestamptz NOT NULL DEFAULT now(), applied_by uuid NOT NULL REFERENCES users(id),
    reversed_at timestamptz, reversed_by uuid REFERENCES users(id), reversal_reason_code varchar(30)
  );
  CREATE INDEX ON payment_applications(scheduled_payment_id) WHERE reversed_at IS NULL;
  CREATE INDEX ON payment_applications(source_type, source_id) WHERE reversed_at IS NULL;
  REVOKE UPDATE, DELETE ON payment_applications FROM app_role;   -- append-only : on « reverse », on ne corrige pas
  -- Vue solde
  CREATE VIEW v_invoice_balance AS
    SELECT i.id AS invoice_id, i.total_amount,
           COALESCE(SUM(pa.amount + pa.discount_taken + pa.write_off) FILTER (WHERE pa.reversed_at IS NULL),0) AS settled,
           i.total_amount - COALESCE(SUM(pa.amount + pa.discount_taken + pa.write_off) FILTER (WHERE pa.reversed_at IS NULL),0) AS balance
      FROM invoices i LEFT JOIN payment_applications pa ON pa.invoice_id = i.id GROUP BY i.id;
  -- UN SEUL écrivain de invoices.paid_amount / scheduled_payments.amount_paid :
  CREATE FUNCTION fn_sync_settlement() RETURNS trigger … -- AFTER INSERT OR UPDATE OF reversed_at ON payment_applications
    -- 1) UPDATE scheduled_payments SET amount_paid = Σ actives, status = CASE … ;
    -- 2) UPDATE invoices SET paid_amount = Σ actives (amount + discount + write_off), payment_status = CASE … ;
    -- 3) RAISE si Σ actives d'une échéance > amount_due + 0.01 (garde sur-paiement déplacée en base) ;
    -- 4) RAISE si Σ applications actives d'un paiement > payments.amount − withholding (garde « on n'applique pas plus que le paiement »).
  ```
