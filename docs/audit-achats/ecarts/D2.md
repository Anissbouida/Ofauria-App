### G-D2-01 — La DA n'est pas un document : mono-table sans en-tête, sans numéro, sans date de besoin, sans consommable

- **Capacités / faiblesses** : C-D2-01 ; W-39 (consommables exclus), W-51 (pas d'audit), W-65 (traçabilité invisible).
- **Preuve** : `server/migrations/057_purchase_requests.sql:2-18` (`ingredient_id UUID NOT NULL … ON DELETE CASCADE`, pas de `packaging_id`, `unit VARCHAR(20)` libre, `reason` texte) ; `purchase-request.repository.ts:24-41` (`JOIN ingredients` dur, les consommables ne peuvent pas exister) ; `bon-sortie.repository.ts:778` (`AND bsl.ingredient_id IS NOT NULL` : les ruptures emballage ne remontent jamais) ; SQL : 31 DA, `COUNT(*) FILTER (WHERE pr.unit <> ing.unit)` = 0 (l'unité est toujours celle de la fiche, elle n'apporte rien) ; `ON DELETE CASCADE` sur l'ingrédient → l'historique d'une DA disparaît avec sa fiche.
- **Manque vs standard** : SAP EBAN, D365 PurchReqTable/Line, ORA, NS modélisent **en-tête (demandeur, objet, date requise, statut agrégé) + lignes (article ou catégorie, quantité, unité, date de besoin, fournisseur suggéré)**. Ici il n'y a ni regroupement « la demande du chef pâtissier du mardi », ni numéro à citer au téléphone, ni date de besoin, ni ligne « catégorie » (une charge sans article), ni ligne consommable.
- **Impact métier** : le magasinier crée 6 DA pour 6 ingrédients d'un même BSI, l'acheteur ne sait pas ce qui va ensemble ; aucun « pour quand » ; 109 consommables (cartons, boîtes, films) hors circuit alors que `purchase_order_items.packaging_id` existe (mig 110).
- **Priorité** : **P1** (chaque DA d'emballage se fait aujourd'hui par téléphone ou BC direct).
- **Conception cible** (pattern D365, matrice C-D2-01) :

```sql
-- 305_request_line_po_lines.sql
CREATE TABLE request_line_po_lines (
  request_line_id uuid NOT NULL REFERENCES purchase_request_lines(id),
  po_line_id      uuid NOT NULL REFERENCES purchase_order_items(id),
  qty_base        numeric(14,4) NOT NULL CHECK (qty_base > 0),   -- part de la ligne DA couverte par cette ligne BC
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid REFERENCES users(id),
  PRIMARY KEY (request_line_id, po_line_id)
);
-- Couverture dérivée : commandé = Σ qty_base des BC non annulés ; reçu = au prorata de la réception de la ligne BC
CREATE VIEW v_request_line_coverage AS
SELECT l.id AS request_line_id, l.qty_base AS qty_requested_base,
       COALESCE(SUM(x.qty_base) FILTER (WHERE po.status <> 'annule'), 0)                       AS qty_ordered_base,
       COALESCE(SUM(x.qty_base * LEAST(1, poi.quantity_delivered / NULLIF(poi.quantity_ordered,0)))
                FILTER (WHERE po.status <> 'annule'), 0)                                         AS qty_received_base,
       CASE WHEN l.status IN ('cancelled','rejected') THEN l.status
            WHEN l.closed_at IS NOT NULL THEN 'closed'
            WHEN COALESCE(SUM(x.qty_base) FILTER (WHERE po.status <> 'annule'),0) = 0 THEN 'pending'
            WHEN COALESCE(SUM(x.qty_base * LEAST(1, poi.quantity_delivered / NULLIF(poi.quantity_ordered,0))) FILTER (WHERE po.status <> 'annule'),0) >= l.qty_base - 0.0001 THEN 'received'
            WHEN COALESCE(SUM(x.qty_base) FILTER (WHERE po.status <> 'annule'),0) >= l.qty_base - 0.0001 THEN 'ordered'
            ELSE 'partially_ordered' END AS coverage_status
FROM purchase_request_lines l
LEFT JOIN request_line_po_lines x ON x.request_line_id = l.id
LEFT JOIN purchase_order_items poi ON poi.id = x.po_line_id
LEFT JOIN purchase_orders po ON po.id = poi.purchase_order_id
GROUP BY l.id;
```

  - Quand D4 livrera `po_line_events` (P1/P2 de la matrice), `qty_received_base` se lit dans la vue d'événements au lieu du cumul `quantity_delivered` ; la vue ci-dessus reste l'interface.
  - **Règles** : (1) une annulation de BC (`annule`, `non_livre`, suppression) ne touche **aucune** ligne DA : la vue retombe en `pending` d'elle-même ; (2) `closed_at` est posé **à la main** (« clôturer le reliquat », motif) ou automatiquement quand `coverage_status='received'` pendant N jours (job) ; (3) `already_ordered` devient : `EXISTS (SELECT 1 FROM purchase_request_lines l JOIN v_request_line_coverage c USING(request_line_id…) WHERE l.origin_ref_type='bsi_line' AND l.origin_ref_id = bsl.id AND c.coverage_status <> 'received' AND l.status NOT IN ('cancelled','rejected'))` — **par ligne BSI**, et l'écran propose « Ajouter au besoin existant » au lieu de masquer ; (4) `DELETE FROM purchase_orders` interdit si une ligne figure dans `request_line_po_lines` (trigger `BEFORE DELETE`, ou mieux : plus de DELETE physique, cf. CREATE OR REPLACE FUNCTION fn_stock_forecast(p_store uuid, p_horizon date)
RETURNS TABLE (purchasable_kind text, purchasable_id uuid, stock_usable_base numeric, on_order_base numeric,
               planned_needs_base numeric, forecast_base numeric) AS $$
  WITH stock AS (   -- lots actifs, non périmés à l'horizon (FEFO dans le besoin, VERT A.2)
    SELECT 'ingredient', l.ingredient_id, SUM(l.economat_quantity + l.pesage_quantity)

       AND (l.expiration_date IS NULL OR l.expiration_date >= p_horizon) GROUP BY 2
    UNION ALL
    SELECT 'packaging', pss.packaging_id, pss.stock_quantity FROM packaging_store_stock pss WHERE pss.store_id = p_store),
  on_order AS (     -- BC confirmés non reçus : commandé − reçu − annulé (D4 ajoutera quantity_cancelled)
    SELECT CASE WHEN poi.ingredient_id IS NOT NULL THEN 'ingredient' ELSE 'packaging' END,
           COALESCE(poi.ingredient_id, poi.packaging_id),
           SUM(GREATEST(poi.quantity_ordered - poi.quantity_delivered, 0))
      FROM purchase_order_items poi JOIN purchase_orders po ON po.id = poi.purchase_order_id
     WHERE po.store_id = p_store AND po.status IN ('en_attente','envoye','livre_partiel')

       AND NOT EXISTS (SELECT 1 FROM production_bons_sortie bs WHERE bs.plan_id = pp.id AND bs.status IN ('pret','remis','cloture'))
     GROUP BY 2)
  SELECT k, id, COALESCE(s,0), COALESCE(o,0), COALESCE(n,0), COALESCE(s,0)+COALESCE(o,0)-COALESCE(n,0)
    FROM (…FULL OUTER JOIN des trois CTE sur (kind,id)…) t;
