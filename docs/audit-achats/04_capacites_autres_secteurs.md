# 04 — Capacités Achats des autres secteurs (au-delà de la boulangerie)

Date : 2026-10-12. Complète `02_benchmark_erp.md` (127 capacités `C-Dx-nn`, pensées pour une boulangerie-pâtisserie au Maroc). Cible : SaaS multi-industries pour PME de 10 à 500 salariés, Maroc puis Afrique francophone. Lecteur : ancien développeur Oracle Forms / PL*SQL.

## 0. Méthode

- **Six profils étudiés** (codes utilisés dans les tableaux) : **NEG** distribution / négoce / import ; **IND** industrie manufacturière ; **RES** restauration multi-sites / hôtellerie ; **BTP** BTP / projets ; **SRV** services / bureaux ; **SAN** santé / pharmacie / cosmétique. **AGRO** désigne le profil d'origine (boulangerie).
- **ERP de PME de référence** : **ODOO** (17/18, CE sauf mention EE), **BC** (Dynamics 365 Business Central), **B1** (SAP Business One), **X3** (Sage X3), **NS** (NetSuite). D365 F&O, S/4 et Oracle Fusion ne sont cités que lorsqu'ils sont les seuls à couvrir le point.
- **Confiance** : `[v]` = vérifié par une recherche web du 2026-10-12 (sources en fin de document) ; `[c]` = connaissance du produit, confiance moyenne, à confirmer sur une base de démo avant de s'en servir comme argument commercial.
- **Pertinence** pour un SaaS PME multi-industries : **essentiel** (sans elle, un secteur entier ne peut pas utiliser le module) ; **utile** (attendue par la majorité des clients d'un secteur) ; **optionnel**.
- **Couche** : **noyau** (tous les tenants) ; **pack sectoriel** (activé par `tenant_modules`, cf. plan SaaS) ; **pack pays** (Maroc, Sénégal, Côte d'Ivoire…).
- **Impact schéma** : deux temps. **Maintenant** = ce qu'il faut poser dans la refonte pour ne pas casser le schéma plus tard (colonne, clé, type énuméré extensible). **Plus tard** = tables et écrans à construire au premier client du secteur.
- Une capacité `N-Dx-nn` est **nouvelle** (absente de la matrice) ou **sous-couverte** (présente mais jugée hors-sujet/optionnelle pour la boulangerie, ou modélisée de façon trop spécifique). Les sous-couvertures sont listées en section 2 ; on ne les duplique pas dans la section 3 quand une simple révision de pertinence suffit.

## 1. Synthèse

1. **La matrice C-xx tient pour le processus**. Le cycle DA → BC → réception → facture → paiement → GR/IR, les axes de statut, les événements append-only et le lettrage N:N valent pour tous les secteurs. Ce qui ne tient pas, ce sont **les objets** : la matrice raisonne avec « ingrédient / emballage », « contenant », « kg / L / pièce », « DLC », « zone d'atelier », « compte 4411 ». Ces notions sont des cas particuliers de concepts plus généraux.
2. **Six trous de modèle**, à combler dans le schéma dès la refonte : (a) un **article générique** avec type, politique de suivi (aucun / lot / série) et méthode de valorisation, à la place de `(purchasable_kind, purchasable_id)` ; (b) des **unités de mesure libres** (m², h, jour, ml, boîte) ; (c) une **imputation analytique multi-axes par ligne** (projet, tâche, centre de coût, site, OF) ; (d) la **devise et le taux sur chaque pièce**, avec un montant en devise société ; (e) une organisation **entité juridique ≠ site ≠ emplacement** ; (f) un **référentiel fiscal par pays** (identifiants, taxes, comptes par rôle) au lieu de colonnes `ice`, `if_number` et de comptes PCM écrits en dur.
3. **Trois flux sectoriels** n'existent pas dans la matrice et coûtent cher à rajouter si le schéma ne les prévoit pas : la **sous-traitance avec envoi de composants** (IND), le **dossier d'import** avec frais d'approche multi-factures et devise (NEG), et la **facturation à l'avancement avec retenue de garantie** (BTP). Il suffit aujourd'hui de leur laisser une prise : une référence de besoin générique sur la ligne, des emplacements de type `supplier` / `transit`, une allocation de frais d'approche vers des lignes de réception de plusieurs BC, et des échéances typées.
4. Au total, **55 capacités N-xx** : 18 essentielles (14 sont avant tout des décisions de schéma du noyau ; 4 ne sont essentielles que pour leur secteur : sous-traitance, dossier d'import, facture d'import, rappel réglementaire), 29 utiles, 8 optionnelles. Répartition par domaine : D1 8, D2 4, D3 3, D4 9, D5 7, D6 6, D7 3, D8 6, D9 3, D10 6. **12 lignes de la matrice C-xx** changent de pertinence ou de couche (section 2).
5. Ce qu'il ne faut **pas** faire : construire maintenant la sous-traitance, le MRP multi-niveaux, les plans de contrôle qualité, les situations de travaux, le crédit documentaire ou les cautions. Aucun de ces objets n'impose de casser le noyau s'il est ajouté plus tard, pourvu que les huit points de la section 4 soient en place.

## 4. À prévoir dans le schéma dès la refonte

Liste courte, par ordre de priorité. Chaque point évite une migration destructrice ultérieure (changement de clé, éclatement de table ou réécriture de toutes les lignes de document). Ce sont des colonnes et des tables, pas des écrans.

1. **`items` unique** (N-D1-01) : `item_type`, `tracking_policy` (none / lot / serial), `expiry_required`, `costing_method`, `base_uom_id`, `is_catch_weight`, `template_id` (variantes), `manufacturer_party_id`, `hs_code`, `origin_country`, `gross_weight`, `volume`, `storage_temp_min/max`. Les tables `ingredients` et `packaging_items` deviennent des extensions 1:1, et **toutes les lignes de document portent `item_id`**. C'est la décision qui coûte le plus cher à repousser : chaque nouvelle table de lignes conçue sur `(purchasable_kind, purchasable_id)` serait à refaire.
2. **Unités et conditionnements génériques** (N-D1-02) : `uom_categories`, `uoms`, `item_uom_conversions` (densité incluse), `item_packagings` (remplace `container_types` + `qty_per_container`). Sur les lignes : `uom_id`, `qty`, `factor_to_base` (snapshot), `qty_base` générée.
3. **`line_type` sur toutes les lignes** (N-D4-01) : `item`, `service`, `charge`, `asset`, `subcontract`, `text`, plus `disbursement` sur les factures.
4. **`dimension_set_id` sur toutes les lignes** de DA, BC, réception, facture et écriture (N-D4-02, N-D10-01) : tables `analytic_dimensions`, `dimension_values`, `dimension_sets`, `dimension_set_entries`, `dimension_rules`. Répartition en % seulement sur les factures et les écritures. Le projet, le chantier, le centre de coût et l'OF sont des valeurs de dimension, pas des colonnes.
5. **Devise sur chaque pièce monétaire** (N-D4-03) : `currency`, `exchange_rate`, `rate_date` sur l'en-tête, `amount_company` sur les lignes et dans les écritures, table `currency_rates`. Valeur par défaut MAD et 1, donc rien ne change pour la boulangerie.
6. **Organisation : `legal_entity_id` + `site_id` sur chaque en-tête, `locations.location_type`** (N-D10-02, N-D4-05, N-D5-03) avec les types `internal`, `supplier`, `customer`, `transit`, `scrap`. `po_schedules.ship_to_site_id` ; prix et accords avec `legal_entity_id` / `site_id` NULL résolus par spécificité (N-D1-06).
7. **Tiers unique et identifiants fiscaux par pays** (N-D10-04, N-D1-08) : `parties` + `party_tax_ids(scheme, value)` ; `suppliers.party_id`. ICE, IF, RC et TP deviennent des lignes `MA_*`.
8. **Comptes par rôle** (N-D8-06) : `account_roles` + `tenant_account_mapping` ; `posting_profiles` visent un rôle. Aucun numéro PCM en dur.
9. **Lots génériques** (N-D5-01) : `stock_lots(item_id, lot_no, is_serial, supplier_lot_no, expiry_date, warranty_until, status ∈ (quarantine, available, blocked, recalled, consumed))` + `reception_voucher_lots` ; `ingredient_lots` migré ou exposé en vue ; `recalls` + `recall_lots` (N-D10-03).
10. **Référence de besoin sur les lignes de DA et de BC** (N-D2-01) : `demand_ref_type`, `demand_ref_id`, `reserve_on_receipt`. Elle porte l'achat pour un OF, une opération sous-traitée, une tâche de chantier ou une commande client.
11. **Échéances typées** (N-D6-02) : `scheduled_payments.installment_kind` (`normal`, `retention`, `advance_recovery`, `prepayment`) + `release_condition` + `released_at`.
12. **Frais d'approche multi-BC et estimé / réel** (N-D5-02) : `landed_cost_allocations(receipt_item_id)` sur des réceptions de plusieurs BC, plusieurs factures de frais par dossier, statut `estimated` / `actual` ; `reception_vouchers.inbound_shipment_id NULL` (FK posée plus tard).
13. Colonnes légères à ajouter tout de suite parce qu'elles ne coûtent rien : `purchase_orders.incoterm_code` / `incoterm_place` ; `item_revision` sur les lignes de BC et de réception ; `invoice_items.service_period_from/to` ; `purchase_agreements.kind` (+ `notice_days`, `auto_renew`) ; `compliance_documents.res_type` (fournisseur, article, lot) ; `country_code` sur les tables fiscales (`tax_codes`, `fiscal_thresholds`, `withholding_rates`).

Règle de conception qui découle de ces points : **tout type métier susceptible de s'étendre par secteur** (type de ligne, type de pièce, statut d'agrément, type de document de conformité, type de référence de besoin, mode de paiement, type d'emplacement) est stocké dans une **table de référence** avec une FK, ou dans un `text` contrôlé par `CHECK` modifiable par migration de pack. On évite l'`enum` PostgreSQL, dont on ne peut pas retirer une valeur et qui ne peut pas varier par tenant.
